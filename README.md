# rssmix

**Note**: Neither this code nor myself are in any way, shape or form associated with the website rssmix.com.

This code was inspired by the website's intermittent availability in late 2021.

## Components

This software was designed to be modular and consists of four pieces. Two of them are required (`fetcher`
and `compiler`), while `api` and `publisher` are optional.

### API

`api` provides a REST API to manage the underlying database. It can:
*  Create new compilations
*  Update existing compilations
*  Delete compilations
*  Remove obsolete feeds
*  Provide basic statistics

See the `api/` folder for more information/documentation.

As you can manage the database directly, this component is optional but very useful.

### Fetcher

The `fetcher` has a simple job: It obtains copies of all feeds and stores them locally.
It updates the `feed_status` table to keep track of when feeds have been retrieved last.

This component is essential and must be running continually.

### Compiler

The `compiler` merges the data of multiple feeds into a new, single feed.
It reads the `feed_status` table (previously updated by `fetcher`) to determine which compilations
have new data available and rebuilds them. It writes the result into the local filesystem as a
single RSS file.

This component is essential and must be running continually.

### Publisher

To enable a clean separation of frontend and backend, the `publisher` can be used to upload
files generated by `compiler` to a webserver, CDN or other publicly reachable service.
To achieve this, publisher calls a shell script or binary whenever a compilation has been updated
by the `compiler`. If this script/binary returns success (exit code 0), `publisher` will mark
it as successful.

If you are running all components on a single system, this component is not needed.

## Database

All components support both MySQL/MariaDB and SQLite as a database backend.
You can find the schema for each in the `sql/` folder.
There are currently no indices but these may be helpful in a big(ger) installation.

## Compiling

Go 1.26 or newer is required. A Makefile is provided, so running `make`
builds all four binaries with `CGO_ENABLED=0` by default. Cross-compilation does
not require a C toolchain, for example:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 make
```

SQLite uses `modernc.org/sqlite` (pure Go). Existing SQLite files and the
configuration value `database.type: sqlite3` remain supported; no database
conversion is needed. The compatibility driver in `lib/sqlite.go` preserves
a five-second busy timeout on every connection, with DSN overrides supported.
Run library tests separately because `lib` is a nested Go module:

```sh
CGO_ENABLED=0 go test ./...
(cd lib && CGO_ENABLED=0 go test ./...)
```

## Configuration

Each component uses a YAML file for its configuration. Examples can be found in the `etc/` folder,
containing all available settings.

## Compiler consistency

Fetcher and compiler now track content revisions in SQLite, independent of
wall-clock timestamps. They automatically add `feed_revision` and
`compilation_build_state` at startup without altering the existing tables.
Deploy and restart both workers together. The first run rebuilds configured
compilations; the existing output is kept until the build succeeds.

A compilation is replaced only if every assigned source can be read and parsed.
`feed_status.active = 0` only pauses fetching: the compiler continues using that
source's last downloaded file. A source is excluded only when its association
in `compilation_content` is removed. A paused source with missing or invalid cache
still prevents replacing the output. If no sources are assigned, the previous
output is retained and an error is logged. A valid feed containing zero items
is still accepted as an empty feed.

Source revisions and the configuration used for a successful build form a
snapshot. Source changes during compilation stay queued, even if two versions
arrive within the same second. The compiler also detects changes to source
membership, filters, title, destination and item limit. Source hashes guard the
interval between the fetcher's atomic file replacement and its database commit.
If that database commit fails, the next successful check records the new content
version even when the cache already contains identical bytes.

Build the compiler and fetcher as packages (`go build ./compiler` and
`go build ./fetcher`) or use `make`; both have multiple source files.
Backoff and HTTP validators are stored in SQLite (see below).

### Download validation

Before replacing a cached feed, the fetcher validates the complete response.
XML must be well formed, have a supported RSS/RDF/Atom root and, for RSS/RDF,
exactly one direct channel. Trailing garbage, additional roots, duplicate
attributes and nesting deeper than 256 elements are rejected. This checks
structure and parser compatibility, not full RSS/Atom specification compliance.
Valid empty feeds and JSON Feed remain supported. HTTP Content-Type alone is
not used to accept or reject a feed.

Rejected downloads leave the previous cache, HTTP validators and database
revision intact. Temporary downloads are removed. Existing caches are validated
before conditional requests are enabled; successful validation is recorded in
SQLite. The compiler's feed parser must also accept the data.
External XML entities are not resolved. No additional database migration is
needed for download validation.

### Fetcher state in SQLite

The fetcher creates `fetcher_host_state`, `fetcher_http_state` and
`fetcher_state_migration` automatically at startup. No manual ALTER TABLE is
required. Host records contain the next request time, cooldown, failure count
and resume URL. HTTP validators are keyed by the original feed URL and remain
bound to the SHA-256 of the accepted cache. Missing or changed caches cannot
use stale validators. Timestamps are UTC RFC3339 with fractional seconds;
an empty string means no scheduled time.

On the first start for each database, the fetcher imports
`workdir/rssmix-fetcher-state.json` and the `.http.json` files next to the
configured feed caches, respecting `subdirs`. All configured feeds are
considered, including inactive ones. Existing SQLite records take precedence.
The import and its completion marker commit in one transaction. A failed import
can be retried safely. Invalid backoff JSON stops startup to avoid losing a
cooldown; malformed or mismatched HTTP metadata is skipped with a warning,
causing a full GET instead.

After the import commits, JSON files are neither read nor written. They remain
unchanged and may be archived or removed after checking the migration log.
Keep the configured workdir unchanged during this first start so existing
metadata can be found. Missing JSON files are allowed; the completed import
will not be repeated if files appear later. Sources added later use fresh HTTP
state. A downgrade to an old fetcher would use the stale JSON files, so it does
not restore the current SQLite scheduling state automatically.

Only one fetcher process should use a database. Stop the old fetcher before
replacing its binary; the compiler can continue running. Backoff delays,
per-host pacing, `active=0` behavior and download validation are unchanged.
Back up SQLite using its backup facility; cached feed bodies and generated
compilations remain separate files and still need their own backups.

### Filter lists containing commas

New API writes store each include/exclude list as a versioned JSON array in
its existing `filter_inc` or `filter_exc` TEXT column. The storage prefix is
`(?rssmix-filters:v1)`, followed by an array, for example:

```text
(?rssmix-filters:v1)["^Folge [0-9]{1,3}$","^Alpha,Beta$"]
```

The prefix distinguishes the new format from legacy regular expressions,
including character classes such as `["abc"]` that look like JSON arrays.
No new columns or automatic rewriting of existing filter values are needed.
The HTTP API continues accepting and returning ordinary string arrays; clients
must not add the storage prefix to their request patterns.

Existing untagged values retain their comma-separated interpretation, including
the historical treatment of invalid fragments. A previously stored expression
containing commas cannot be repaired unambiguously: resubmit the intended list
through the updated API (or write the tagged format explicitly). Existing
compilations are not automatically migrated.

For PATCH, an omitted list or `null` leaves that list unchanged; `[]` clears only
that list. New regexps are validated before request changes are saved; invalid
patterns return HTTP 400. Within each list, alternatives are ORed. Include and
exclude are both applied: include must match (unless empty), and exclude must
not match. An empty string inside a new list is an actual empty regexp, which
matches every title; use `[]` to clear a list.

Corrupt or unsupported tagged data is an error, never a fallback to legacy
splitting. Invalid tagged regexps stop compilation and keep the previous output
and successful snapshot. Filter changes continue to queue a rebuild even when
source content has not changed.

Deploy the updated compiler before enabling the updated API to write new lists.
An old compiler cannot read the tagged format. The fetcher is unchanged. For an
installation that runs only fetcher/compiler, only the compiler binary needs to
be replaced for this patch. Rebuild consumers of the local `lib` module normally.

### Command-line help

All four binaries accept `-h` and `--help`. They print usage, the build version
and configuration search paths to stdout, then exit successfully before loading
configuration or opening a database. Unknown options or positional arguments
print an error to stderr and exit with code 2. Running without arguments starts
the service as before. No configuration-path option is introduced.

### Password hashing

The API stores passwords as Argon2id hashes using `alexedwards/argon2id` and
`golang.org/x/crypto`. New hashes use 64 MiB, three iterations, two lanes,
a random 16-byte salt and a 32-byte key. Hash parameters and salt are included
in the encoded hash. Argon2 operations are serialized per process to bound
memory usage. Stored parameters are checked before verification.

At API startup, a SQLite transaction adds `compilation.password_hash` if needed,
hashes each nonempty legacy `password` and clears that plaintext field. Repeated
startup does not rehash migrated credentials. Empty/NULL passwords remain
passwordless. A literal legacy password beginning with `$argon2id$` is still
hashed as plaintext: the separate column makes the distinction unambiguous.
Migration errors roll back schema and credential changes. Corrupt hashes or
conflicting plaintext/hash records cause an error; authentication does not fall
back to plaintext. Legacy plaintext inserted after migration also fails closed.

GET remains public by ID. PATCH and DELETE require the existing password when
set (missing: 401, wrong: 403). New/changed passwords are never stored in
plaintext. As before, an omitted or empty PATCH password leaves the current
password unchanged. Credentials are not returned by GET. Query-parameter
password transport is unchanged by this patch.

Before migration, stop any old API processes and create a SQLite backup. Keep
old API binaries stopped after migration: they read the now-empty legacy column
and would interpret migrated compilations as passwordless. Do not downgrade
without restoring a compatible backup. Fetcher/compiler may keep running; they
do not use the password fields. Backups made before migration still contain
plaintext passwords. Clearing a column does not securely erase old SQLite pages,
logs or backups. This patch protects current logical database records.
